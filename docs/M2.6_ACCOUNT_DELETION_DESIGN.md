# MiniDrama — M2.6 Account Lifecycle & Privacy

**Status:** Approved 2026-11-18 · implementing
**Scope:** In-app account deletion, deletion audit, playback de-linking, a static public deletion page.
**Preserves:** M2.2 offline playback · M2.3 API integration · M2.5 authentication (ADR-37…ADR-45) · all ABR benchmarks.

This document is the design of record for M2.6. It was produced as a Phase 1
architecture review, approved with eight decisions and four refinements, and
updated here to carry them.

---

## 1. Approved decisions

| | Decision | Resolution |
|---|---|---|
| D1 | Immediate deletion vs a 30-day grace period | **Immediate.** DATABASE_SCHEMA.md §6's "within 30 days" is a ceiling, not a target. A grace period needs the account to stay sign-in-able, which contradicts immediate session revocation, and a scheduler we do not have (pg-boss deferred, ADR-08). |
| D2 | May a guest delete without a password | **Yes**, with a typed `DELETE` confirmation. A guest has no password; the access token is the only credential that exists for them (ADR-41). |
| D3 | An `AccountDeletion` audit table | **Added.** §6 requires deletion be logged and `AdminAuditLog` is M5. Holds no direct identifiers — see §5. |
| D4 | Public page scope | **Static only in v1.** A web form promising "check your email" while `MAIL_PROVIDER=file` repeats the mistake ADR-42 exists to prevent. The email-initiated flow is designed in §8.2 and ships with a real sender. |
| D5 | Where the public URL lives | **Deferred.** Served by Express today; the public origin follows the deployment decision that SYSTEM_ARCHITECTURE.md §11 still marks `[APPROVAL NEEDED]`. |
| D6 | Endpoint shape | **`DELETE /api/v1/auth/account` with a request body**, as API_DOCUMENTATION.md §2 already advertises. |
| D7 | Rate-limit `POST /auth/change-password` | **In this milestone.** It re-verifies a password and is currently unlimited — a stolen access token gets an unbounded guessing oracle. |
| D8 | Wipe local SQLite on deletion | **Yes**, and only on deletion. `applyAccountChange()`'s deliberate no-wipe rule is unchanged for sign-in and sign-out. |

## 2. Approved refinements

| | Refinement | Where it is answered |
|---|---|---|
| R1 | A 401 after a deletion attempt is not proof of deletion. Distinguish expired auth, invalid credentials, deletion-with-a-lost-response, and revoked sessions. Verify with the server before wiping local data. | §4 (status taxonomy), §7 (receipt mechanism), §9 (client state machine) |
| R2 | `AccountDeletion` carries no direct personal identifiers; define fields, retention, access control and cleanup status. | §5 |
| R3 | Post-commit `PlaybackEvent` de-linking must be observable and recoverable, and a failure discoverable through the reconciliation command. | §6 |
| R4 | Do not publish unverified legal or retention claims; separate technical design from legal requirements needing verification. | §11, §12 |

## 3. Current-architecture findings that shape the design

1. **`Favorite` deletion must decrement `Drama.favoriteCount`.** The counter is denormalised, maintained transactionally by `addFavorite`/`removeFavorite`, and nothing recomputes it (DATABASE_SCHEMA.md §9.5). A bulk `deleteMany` inflates it permanently.
2. **The `User` cascades never fire.** Deletion anonymises the `User` row rather than dropping it, so every child row must be deleted explicitly — which is what we want, since a cascade would bypass (1).
3. **`PlaybackEvent.userId` has no foreign key** (deliberate). Nothing cleans it up. It is also the only unbounded set: a heavy viewer accumulates 20k–60k rows inside the 90-day window.
4. **`POST /auth/change-password` is unrate-limited** and verifies `currentPassword`. Pre-existing gap, closed here (D7).
5. **`applyAccountChange()` deliberately preserves local SQLite.** Right for sign-out, wrong for deletion: `HttpPlaybackSyncAdapter` treats the post-deletion 401 as non-retryable, so orphaned events burn eight attempts into `dead`.
6. **`SessionRevocationReason.ACCOUNT_DELETED` already exists** in the schema. No enum migration needed for revocation.
7. **`mergeGuestInto` also sets `status = 'DELETED'`** on the retired guest row. Any reconciliation that keys on "DELETED users" would therefore catch merged guests too — which is why §6 keys on the `AccountDeletion` row instead.

## 4. Outcome taxonomy (R1)

The client must never infer "deleted" from an HTTP status alone. Four distinct
outcomes, with distinct wire signals:

| Outcome | Wire signal | What it means | Client action |
|---|---|---|---|
| **Deleted** | `200` + body | TX1 committed | Verify receipt is present, then tear down |
| **Re-auth failed** | `403 FORBIDDEN` | Password wrong, or required and absent. **The session is still valid.** | Stay on the screen, show the message inline |
| **Bad request** | `400 VALIDATION_ERROR` | `confirm !== "DELETE"` | Stay on the screen |
| **Access token expired** | `401 TOKEN_EXPIRED` | Ordinary 15-minute expiry mid-flow | Refresh, retry once |
| **Session not usable** | `401 UNAUTHENTICATED` | Revoked elsewhere, password changed, family revoked, **or deleted with a lost response** | **Ambiguous — resolve via the receipt endpoint (§7)** |
| **Unknown** | transport failure / timeout | Nothing is known | **Resolve via the receipt endpoint. Never wipe.** |

**The critical change from the Phase-1 draft:** a wrong re-auth password now
answers **403, not 401**. The caller *is* authenticated — their access token
verified — so a refused password is an authorisation refusal, not an
authentication one. Collapsing the two is what made 401 ambiguous in the first
place. Enumeration resistance (ADR-39) does not apply: the endpoint is
authenticated, so there is no account to enumerate.

`401 UNAUTHENTICATED` remains genuinely ambiguous, because a successful
deletion kills the very token that would have been used to ask again. That
ambiguity is resolved by §7, not by guessing.

## 5. The `AccountDeletion` audit record (R2)

```prisma
enum AccountDeletionSource { IN_APP  WEB  ADMIN }
enum PlaybackCleanupStatus { PENDING  IN_PROGRESS  COMPLETED  FAILED }

model AccountDeletion {
  id     String @id @default(cuid())
  userId String @unique            // the retained, anonymised User.id

  source       AccountDeletionSource @default(IN_APP)
  wasAnonymous Boolean               // guest or registered, for reporting
  requestedAt  DateTime @default(now())
  completedAt  DateTime              // TX1 commit; deletion is synchronous (D1)

  // Aggregate counts. Non-personal: how much, never what.
  removedWatchHistory       Int @default(0)
  removedDramaProgress      Int @default(0)
  removedFavorites          Int @default(0)
  removedSessions           Int @default(0)
  removedVerificationTokens Int @default(0)

  // Playback de-linking lifecycle (§6)
  playbackStatus      PlaybackCleanupStatus @default(PENDING)
  playbackAnonymised  Int       @default(0)
  playbackAttempts    Int       @default(0)
  playbackStartedAt   DateTime?
  playbackFinishedAt  DateTime?
  playbackErrorCode   String?   // a stable code, never a message

  // Deletion receipt (§7)
  receiptHash      String?   @unique  // SHA-256 of a client-generated random id
  receiptExpiresAt DateTime?

  @@index([playbackStatus])
  @@index([requestedAt])
  @@index([receiptExpiresAt])
}
```

**What is deliberately absent, and must stay absent:** email, phone,
`firebaseUid`, `passwordHash`, `displayName`, any raw or hashed session or
verification token, `deviceId`, `ipHash`, `userAgent`, and any episode, drama
or position the person watched. The row answers *that* a deletion happened and
*how much* it removed. It cannot answer *who* or *what they watched*.

`userId` is a random `cuid` on a row whose identifiers have been nulled. It is
not a direct identifier, and it is required: without it the reconciler (§6) has
no subject and the audit record has no referent.

| Property | Value |
|---|---|
| **Retention** | 2 years from `requestedAt`, matching the `AdminAuditLog` figure in DATABASE_SCHEMA.md §6. Enforced by `reconcile:deletions --prune`. |
| **`receiptHash` retention** | 30 days (`receiptExpiresAt`), then nulled by the same command. Recovery past 30 days is pointless, and an unused secret should not persist. |
| **Access control — today** | No HTTP surface at all. Reachable only by the CLI command and direct database access. |
| **Access control — M5** | Admin-only, `SuperAdmin` and `Moderator`. Never exposed on a consumer route. |
| **Logging** | The service logs `userId`, source, and the counts. Never an address, never a token, never a receipt id. |

## 6. Playback de-linking: observable and recoverable (R3)

`PlaybackEvent` nulling runs **after** TX1 commits, because it is the only
unbounded part of the work and the account is already dead without it.
Observability is what makes that safe.

```
TX1 commits
  └── AccountDeletion row inserted with playbackStatus = PENDING
        │
        ▼
  anonymisePlaybackEvents(userId)          ── post-commit, same request
        │
        ├─ set IN_PROGRESS, playbackStartedAt, playbackAttempts += 1
        ├─ loop: UPDATE PlaybackEvent SET userId = NULL
        │        WHERE eventId IN (SELECT eventId FROM PlaybackEvent
        │                          WHERE userId = $1 LIMIT 1000)
        │        accumulate playbackAnonymised
        ├─ success → COMPLETED, playbackFinishedAt
        └─ throw   → FAILED,    playbackErrorCode, playbackFinishedAt
                     (logged; the HTTP response still returns 200 —
                      the account is already gone and the caller can
                      do nothing useful with this failure)

Process dies mid-loop → the row stays IN_PROGRESS forever. That is the
point: an interrupted run is *visible*, not silent.
```

**State transitions**

| From | To | When |
|---|---|---|
| — | `PENDING` | TX1 inserts the row |
| `PENDING` | `IN_PROGRESS` | the sweep starts (sets `playbackStartedAt`, increments `playbackAttempts`) |
| `IN_PROGRESS` | `COMPLETED` | no rows remain for that `userId` |
| `IN_PROGRESS` | `FAILED` | the sweep threw; `playbackErrorCode` set |
| `PENDING` / `IN_PROGRESS` / `FAILED` | `IN_PROGRESS` → `COMPLETED` | the reconciler picks it up |

`COMPLETED` is terminal and is never re-entered.

**The reconciliation command**

```
pnpm --filter @minidrama/backend reconcile:deletions           # report + repair
pnpm --filter @minidrama/backend reconcile:deletions -- --dry-run
pnpm --filter @minidrama/backend reconcile:deletions -- --prune
```

It is a command, not a scheduler, for the reason ADR-35 gives. It:

1. **Finds unfinished work** — every `AccountDeletion` whose `playbackStatus` is
   not `COMPLETED`, plus any whose status *is* `COMPLETED` but for which
   `PlaybackEvent` rows still carry that `userId` (a status that lies is worse
   than one that is behind).
2. **Finishes it**, in the same bounded batches, updating the same fields.
   Idempotent: a second run finds nothing and reports zero.
3. **Reports, without acting on, orphans** — `PlaybackEvent` rows whose `userId`
   points at a `User` with `status = 'DELETED'` that has **no** `AccountDeletion`
   row. These are merged guests (finding 7), whose events were deliberately
   re-pointed by `mergeGuestInto`. Nulling them would destroy attribution the
   merge was careful to preserve, so the command names them and stops.
4. **With `--prune`**: nulls `receiptHash` past `receiptExpiresAt`, and deletes
   `AccountDeletion` rows older than 2 years.

Exit code is non-zero when anything remains unrepaired, so it is usable as a
health check the day there is somewhere to run it.

## 7. The deletion receipt (R1)

**The problem.** A successful deletion destroys the credential that would be
used to ask "did it work?". If the 200 is lost — a dropped connection, a killed
app, a train tunnel — the client is left holding a dead token and no answer.
Wiping local data on a guess risks destroying unsynced progress for an account
that still exists; not wiping risks leaving a deleted account's history on the
handset.

**The mechanism.** The client proves it was the one who asked, using a secret
it generated *before* asking.

```
1. Client generates  receiptId = 32 random bytes, base64url
   and PERSISTS IT to secure storage before any network call.

2. DELETE /api/v1/auth/account
     Authorization: Bearer <access>
     Idempotency-Key: <receiptId>          ← already in the CORS allowlist
     { "password": "...", "confirm": "DELETE" }

3. TX1 stores  receiptHash = sha256(receiptId)  on the AccountDeletion row.

4. 200 response carries  receiptRecorded: true  — the client already holds
   the id, so what it needs confirmed is that the SERVER stored it. A client
   that sees false knows it has no recovery path and says so.

5. If the client did NOT get a 200, it asks:

   POST /api/v1/auth/deletion-receipt        (unauthenticated, rate limited)
     { "receiptId": "<receiptId>" }

   200 { "deleted": true,  "deletedAt": "..." }   → deletion happened
   200 { "deleted": false }                       → it did not
```

**Why this is safe to expose unauthenticated.**

- The receipt id is 256 bits of CSPRNG output known only to the client that
  generated it. Guessing it is the same non-threat as guessing a refresh token.
- The response contains **no account information** — a boolean and a timestamp.
  It cannot be used to discover whether an address, a user id or a device has an
  account, because the only thing it accepts is a secret we minted nothing from.
- It is stored hashed, for the same reason `Session.refreshHash` is: a database
  dump yields nothing usable.
- It is rate limited per source address, with the same looser token allowance
  `reset-password` uses and for the same reason (ADR-43): the thing presented is
  unguessable, so the limit exists to bound a flood, not to stop a search.
- `receiptHash` is `@unique`, so a replayed key cannot create a second deletion
  record.

**Why not reuse the access token or the refresh token.** Both are destroyed by
the deletion they would be used to confirm. The receipt is the only credential
in the system whose *purpose* survives the account.

## 8. API surface

### 8.1 Shipping in M2.6

```
DELETE /api/v1/auth/account          access token   5 / 15 min / userId
POST   /api/v1/auth/deletion-receipt none          30 / 15 min / IP
POST   /api/v1/auth/change-password  access token   5 / 15 min / userId   (D7, new limit)
GET    /account-deletion             none           static page (D4)
```

```jsonc
// DELETE /auth/account — request
{ "password": "...", "confirm": "DELETE" }     // password omitted for a guest

// 200
{ "success": true, "data": {
    "accepted": true,
    "deletedAt": "2026-11-18T10:14:22.901Z",
    "removed": { "watchHistory": 128, "dramaProgress": 9,
                 "favorites": 14, "sessions": 3, "verificationTokens": 1 },
    "message": "Your account and viewing history have been deleted."
} }

// 403 FORBIDDEN       password wrong, or required and not supplied — SESSION STILL VALID
// 400 VALIDATION_ERROR confirm !== "DELETE"
// 401 TOKEN_EXPIRED   refresh and retry once
// 401 UNAUTHENTICATED ambiguous — resolve with the receipt endpoint
// 429 RATE_LIMITED
```

No request in this module carries a `userId`; the caller is `callerOf(req)` and
nothing else (auth.schema.ts rule 1). `removed` mirrors `MergeResult.moved`,
which the client already knows how to render.

### 8.2 Designed, deferred to a real mail sender (D4)

```
POST /api/v1/auth/request-deletion   none   5 / 15 min / IP+email
POST /api/v1/auth/confirm-deletion   none   30 / 15 min / IP
```

`request-deletion` is shaped exactly like `forgot-password`: a neutral
acknowledgement whatever the truth, `503` when `isMailDeliveryAvailable()` is
false, outstanding tokens consumed first, a new `VerificationToken` with
`purpose = ACCOUNT_DELETION` and a **15-minute** TTL — shorter than reset's 30,
because this one is irreversible. `confirm-deletion` reuses the
reset-password consumption logic including the `record.email !== user.email`
check, then calls the same service function the in-app path calls.

The `ACCOUNT_DELETION` enum value ships in M2.6's migration so the later
addition is code only.

## 9. Mobile flow and client state machine

```
Profile → Account → [Delete account]
   │
   ├─ (settings)/delete-account          Screen 1 — what goes, what stays, not undoable
   └─ (settings)/delete-account/confirm  Screen 2 — re-auth
          registered: password field
          guest:      type DELETE
                      "This deletes the temporary account on this device."
```

**Teardown, in this order and no other:**

```
1. stop the sync engine        ← first, or it fires a batch into the gap
2. purgeLocalPlaybackData()    ← dropAll() + migrate(), D8
3. clearCredentials()
4. queryClient.clear()
5. startGuestSession()         ← a fresh anonymous account
6. route Home + "Your account was deleted."
```

**The state machine that decides whether step 1 ever runs (R1):**

```
          send DELETE /auth/account  (receiptId persisted beforehand)
                        │
      ┌─────────────────┼──────────────────┬───────────────────┐
     200              403/400            401                transport
      │                 │            ┌────┴────┐                │
      │                 │       TOKEN_     UNAUTH-              │
      │                 │       EXPIRED    ENTICATED            │
      │                 │            │         │                │
      │                 │       refresh,       └────┬───────────┘
      │                 │       retry once          │
      │                 │            │              ▼
      │                 │            │     POST /auth/deletion-receipt
      │                 │            │              │
      │                 │            │     ┌────────┼─────────┐
      │                 │            │  deleted  not        transport
      │                 │            │  = true   deleted     failure
      │                 │            │     │        │           │
      ▼                 ▼            ▼     ▼        ▼           ▼
   TEARDOWN        stay on      (as per   TEARDOWN  sign out   leave
                   screen,      outcome)            normally,  EVERYTHING
                   inline msg                       ask to     alone;
                                                    sign in    "could not
                                                    and retry  confirm"
                                                               + Retry
```

**Three invariants:**

1. **Local data is wiped only after the server has confirmed deletion** — a 200,
   or a receipt lookup that says `deleted: true`. Never on a bare 401, never on
   a timeout.
2. **A transport failure never clears credentials.** The same rule ADR-45 relies
   on: the server said nothing, so nothing is known.
3. **A persisted `receiptId` is checked on next launch.** If the app was killed
   mid-deletion, the first thing the session bootstrap does is resolve it, and
   complete the teardown if the server says the account is gone.

## 10. Data retention matrix

| Table / field | Personal? | Action | Why |
|---|---|---|---|
| `User.id` | pseudonymous | **retain** | Referent for `PlaybackEvent` and the audit row; required by future `Payment`/`Subscription` (§11). |
| `User.email` / `phone` / `firebaseUid` | **yes, direct** | **null** | Direct identifiers. Also frees the unique constraint so the person may register again. |
| `User.passwordHash` | yes (credential) | **null** | No account to authenticate; a retained hash is only a liability. |
| `User.emailVerifiedAt`, `lastSeenAt` | yes (behavioural) | **null** | — |
| `User.status`, `deletedAt`, `tokensValidFrom` | no | **set** | The deletion itself, and the revocation lever (ADR-40). |
| `User.createdAt` / `updatedAt` | weakly | retain | Not linkable once identifiers are gone. |
| `User.isAnonymous` | no | retain as-is | Reporting only. |
| `UserProfile.displayName` | **yes** | **hard delete row** | A chosen name is personal data. |
| `UserProfile.avatarKey` | yes (pointer) | **hard delete row; object deletion is an open obligation** | Object storage is not implemented (M4). No avatars exist yet, so nothing orphans today — but the obligation must land on the storage provider interface when it is written, or the first upload creates undeletable personal data. |
| `UserProfile.preferredGenres`, `preferredLanguageId` | yes (preference) | **hard delete row** | — |
| `Session.*` (`ipHash`, `userAgent`, `platform`, `deviceId`) | **yes** | **hard delete** | DATABASE_SCHEMA.md §6. Reuse detection protects an account that no longer exists. |
| `VerificationToken.*` | **yes** (`email`) | **hard delete** | Would retain the address we just nulled. |
| `WatchHistory.*` | **yes** (episode-level viewing) | **hard delete** | The most sensitive data in the product. Aggregate counts are denormalised elsewhere and are not recomputed from these rows. |
| `DramaProgress.*` | **yes** | **hard delete** | — |
| `Favorite.*` | **yes** (preference) | **hard delete + decrement `Drama.favoriteCount`** | Finding 1. |
| `PlaybackEvent.userId` | **yes** | **null**, post-commit, observably (§6) | — |
| `PlaybackEvent.sessionId` | pseudonymous; not linkable once `userId` is null | retain | Random per visit to the player; no cross-visit linkage. |
| `PlaybackEvent` remainder | no, once de-linked | **retain under the existing 90-day window** | Not indefinite: ADR-35's sweep deletes on `receivedAt`. De-linked telemetry inside 90 days is the minimum that makes a drop-off curve computable. |
| `Drama.totalViews`, `Episode.viewCount`/`likeCount`, `popularityScore` | no (aggregate) | **retain** | Irreversible aggregates over the whole audience. |
| `AccountDeletion.*` | no direct identifiers | **retain 2 years** (§5) | Proof the request was honoured. |

### Rules for tables that do not exist yet

Recorded now so the milestone that adds them inherits the rule.

| Future table | Milestone | Rule |
|---|---|---|
| `Payment`, `Subscription` | M7 | **Retain** with the `User` reference intact — see §11, this is the one rule with an unverified legal basis. |
| `Device` (push tokens) | M6 | **Hard delete** — a device identifier and a live delivery channel. |
| `Notification` | M6 | **Hard delete**. |
| `ContentReport` | M6 | **Anonymise the reporter**, retain the report. Otherwise deletion becomes a way to withdraw an accusation. |
| `AdminAuditLog` | M5 | Retain 2 years; admin identity is separate from consumer identity. |
| `SearchQuery` | M6+ | Hard delete for the user; 180-day global retention otherwise. |

## 11. Legal requirements requiring verification (R4)

**None of the following has been verified by this project.** They are flagged
assumptions, not findings, and each needs confirmation from someone qualified
before it is relied on or published. The technical design in §1–§10 stands on
its own and does not depend on any of them being true.

| # | Assumption in circulation | Where it came from | Status |
|---|---|---|---|
| L1 | Financial records (`Payment`, `Subscription`) must be retained for a statutory period that overrides an erasure request | DATABASE_SCHEMA.md §6, "the statutory financial-record period" | **Unverified.** The Phase-1 review named "8 years under the Companies Act"; that figure has been **withdrawn** from this document. The *technical* design — retain the rows, keep `User.id` as their referent — is sound regardless of the exact period, because any non-zero retention requires it. The period itself must be confirmed before M7 ships payments. |
| L2 | Deletion must complete within 30 days | DATABASE_SCHEMA.md §6 | **Unverified as a legal figure**, and **moot in practice**: D1 makes deletion synchronous, so any ceiling between "immediate" and "30 days" is satisfied. |
| L3 | India's DPDP Act 2023 imposes specific erasure and timeline obligations on this product | DATABASE_SCHEMA.md §6 and ADR-38's "data minimisation under the DPDP Act" | **Unverified.** The Act is passed; the operative rules and enforcement timeline need checking, as does whether MiniDrama meets any threshold they apply to. The design minimises and erases regardless, which is the defensible position either way. |
| L4 | Google Play requires a public deletion-request URL with specific contents | The AUTH-09 requirement in PRODUCT_REQUIREMENTS.md | **Unverified against the current policy text.** The static page (§12) is built to be useful rather than to a remembered checklist, and the exact policy wording must be read before the Play listing is submitted. |
| L5 | 90 days is a compliant retention period for de-linked playback telemetry | SYSTEM_ARCHITECTURE.md §8 | **A product decision, not a legal finding.** Treated as such throughout. |

**Consequence for everything user-facing:** no statute, regulation, policy name
or legal retention period appears in the public page, in any in-app copy, or in
any API response. They describe only what the system actually does.

## 12. Public deletion page (D4, D5)

`GET /account-deletion` → `apps/backend/public/account-deletion.html`.

One hand-written file. No framework, no JavaScript, no form, no input of any
kind — therefore no enumeration surface and no unauthenticated deletion path.
MiniDrama's dark palette inlined from `@minidrama/ui-tokens` values.

Contents:

- How to delete in the app, in the app's own words: **Profile → Account → Delete account**.
- What is deleted: account and sign-in details, everything watched and where you stopped, saved dramas.
- What is kept, stated plainly and without a legal frame: *"anonymous viewing
  statistics, kept for up to 90 days and not linked to you or your account"*,
  and, once M7 ships, payment records.
- That deletion is immediate and cannot be undone, and that the same email
  address may be used for a new account afterwards with nothing carried over.
- A contact route for someone who has lost access to the app or the device.
- A "last updated" date.

**No claim about any law, regulation or policy appears on this page** (R4).

Hosting (D5): served from the API origin today; the public URL follows the
deployment decision in SYSTEM_ARCHITECTURE.md §11. Nothing in M2.6 blocks on it.

## 13. Security threat analysis

| # | Threat | Mitigation | Residual |
|---|---|---|---|
| T1 | Deleting another account by supplying its id | No `userId` in any request schema; identity only from `callerOf(req)` | none |
| T2 | Stolen access token deletes a registered account | Password re-verification | none for password accounts |
| T3 | Stolen access token deletes a **guest** account | Guests have no password; the token is the only credential (ADR-41) | **accepted (D2)** — loss limited to anonymous, device-local history |
| T4 | Delete endpoint as a password oracle | 5 / 15 min keyed on `userId`; the same limiter now on `change-password` (D7) | bounded |
| T5 | Enumeration via the public page | v1 accepts no input at all | none |
| T6 | Receipt endpoint used to probe for accounts | Accepts only a 256-bit secret we never issue publicly; returns a boolean and a timestamp, no account data | none |
| T7 | Receipt replayed to force a second deletion | The receipt endpoint only **reads**. It cannot delete anything. `receiptHash` is unique | none |
| T8 | Deletion link replayed (§8.2, future) | Single-use `VerificationToken`, 15-min TTL, conditional `updateMany` consumption | none |
| T9 | Mailbox compromise destroys an account (§8.2, future) | 15-min TTL; token bound to the address current at consumption | accepted, strictly narrower than password reset |
| T10 | Partial deletion leaves recoverable personal data | Everything personal is inside TX1. The post-commit step touches one analytics column, with explicit status and a reconciler | none |
| T11 | Session survives deletion | Three independent kills: session rows deleted, `tokensValidFrom` moved, `status != ACTIVE`. `SessionIdentityProvider` fails on any one | none |
| T12 | Deletion races a guest merge | `assertUsable` refuses a `DELETED` target; a deleted guest's rows are already gone. Covered by a test | low |
| T13 | Post-deletion playback uploads | 401, non-retryable; moot because teardown wipes the outbox | none |
| T14 | Sensitive data in logs | `userId`, source and counts only. Never an address, token or receipt id | none |
| T15 | Re-registration inherits old data | Impossible: all engagement rows are deleted and a new `User.id` is minted | none |
| T16 | CSRF | Bearer tokens only, no cookie auth anywhere | none |
| T17 | Client wipes local data on an unconfirmed deletion | §9 invariant 1: wipe only after a 200 or a positive receipt | none |
